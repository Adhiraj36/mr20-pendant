Can we control it? Yes — tested end to end

Recording start/stop, haptics, telemetry, file listing and byte-exact downloads all confirmed against the device.

Can we write firmware? A documented path exists

The spec describes a complete upload sequence over Bluetooth. What we lack is a correctly packaged image, which needs the chip's SDK.

Can we drive the LED? No — 21 spellings refused

Every candidate returned DEV&UNKNOWN. The indicator is firmware-driven, so changing it means flashing.

Correction

The spec's command names are wrong

The manufacturer's document writes every command as XS_BLE&… and every reply as XS_DEV&…. On firmware V1.2 those are rejected with DEV&UNKNOWN. The shipped build drops the XS_ entirely.

Because other units may ship the documented dialect, our client sends a probe on connect and adopts whichever prefix answers. Everything below is written in the V1.2 form.

Field notes

Three things that will bite you

File transfers and live audio share one channel

Downloads arrive on the same notify characteristic that streams live audio. Pull a file while the device is recording and the two interleave: our first sync run produced files 8–20 kB larger than their declared size, structurally valid MP3 but containing audio that was never part of the recording. Stop recording before syncing. With it stopped, every transfer was byte-exact.

BLE&STATUS silently stops recording

Undocumented, and it answers DEV&STO — it appears to halt an in-progress recording rather than report anything. Probing an unknown command space is not side-effect free on this firmware.

Two details that cost us time

File names over Bluetooth carry no .mp3 extension, though the same files show one over USB. And the device drops transfer requests issued back to back — a two second gap between files turned four failures out of eight into zero.

Bluetooth protocol

The GATT interface

One service carries everything. Commands are ASCII written to …20a2; replies notify on …20a3; bulk data — live audio and file transfers alike — notifies on …20a1. Our unit does not advertise this service UUID, so scanning for it finds nothing; it advertises as YLF20_<mac suffix> and only reveals the service after you connect.

Limits

What Bluetooth cannot do

Everything here is firmware territory. This list is now backed by probing, not just the absence of a documented command.

  • Drive the LED. Twenty-one spellings, all refused.
  • Arm itself at power-on. You can start a recording, but boot behaviour is fixed. The mitigation is good, though: recording continues after Bluetooth disconnects, so a host only has to connect long enough to start it.
  • Change the recording mode. Call and Conversation can be read, never set.
  • Change audio quality, mic gain, or voice-activation. 16 kHz mono at 32 kbps is fixed.
  • Read raw flash or dump the existing firmware.
Firmware

The two ways in

Writing firmware is not the blocker. Producing an image the bootloader accepts is. The stock build is Zephyr RTOS — the mass-storage identity strings say so outright — which means custom firmware is a Zephyr application against an Actions board port, not a from-scratch reverse-engineering effort.

Documented over-the-air path (untested — we have no valid image)
StepMessageDetail
1. AnnounceBLE&OTA&lenImage size as exactly six digits
2. Device readyDEV&OTASend nothing else until finished, or it fails
3. Stream—244-byte frames, at least 8 ms apart; 20 ms on iOS
4. CommitBLE&OT&OVERConfirmed by DEV&OT&OVER, refused with DEV&OT&ERR

The second route is ADFU, the recovery bootloader in the chip's ROM, which Actions parts expose at USB id 10d6:10d6 — usually entered by holding a button while connecting power. It rewrites flash wholesale, bypassing whatever validation OTA enforces. We have not yet confirmed this pendant will enter it; the test is read-only and erases nothing.

To go further we need the board support package for the exact chip, the image packaging format, and ideally the pin mapping for the microphone, button, LED and haptic. The manufacturer already shared the protocol spec, so asking them is the fastest route — and worth mentioning that the spec they sent does not match the firmware they shipped.

Proof of concept

What we built

A Python client for the protocol and a sync daemon that keeps the pendant recording and pulls everything into a local library, skipping what it already has. Destructive commands are refused unless explicitly unlocked, and the daemon will not take the host off its own network unless it knows how to put it back. 

# our unit does not advertise the service, so probe a likely address
mr20.py --address <uuid> probe
mr20.py --address <uuid> info
mr20.py --address <uuid> shake      # proves hardware control
mr20.py --address <uuid> listen --seconds 20

# continuous sync: record always, pull everything, never re-fetch
mr20sync.py --library ~/pendant --address <uuid> --no-wifi

Seventy-nine automated checks cover protocol parsing, the safety gate (including proof that a blocked command never reaches the wire), MP3 frame alignment, library round-trips and the network guard. All pass. On the device, eight recordings totalling 5.5 MB synced byte-exact, verified by md5 against an independently captured copy.
